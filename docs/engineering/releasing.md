# Stable release operations

A stable release is triggered by `.github/workflows/release.yml` on a `vMAJOR.MINOR.PATCH` tag in the
canonical repository. Do not upload official assets locally, do not give pull-request workflows
release permission, and do not write the updater private key into the command line, files, logs, or a
workflow summary.

## Initial configuration

1. Create an environment named `release` on GitHub, configure required reviewers, and restrict it to
   protected `v*` tags.
2. Create a tag ruleset: block deletion, movement, and force updates of `v*` tags, and allow only
   maintainers to create stable tags on commits whose required checks have passed on `main`.
3. Configure exactly these secrets, and only these, in the `release` environment:
   `AI_ROUTER_UPDATER_PUBLIC_KEY`, `TAURI_SIGNING_PRIVATE_KEY`,
   `TAURI_SIGNING_PRIVATE_KEY_PASSWORD`.
4. Save the encrypted private key and the recovery instructions to a separate offline location, and
   run a signing recovery drill that does not touch the production app.
5. Keep the repository's default `GITHUB_TOKEN` read-only; the release job obtains `contents: write`,
   `id-token: write`, and `attestations: write` only after environment approval.

The public-key value is the content of the base64-encoded minisign public-key file generated by Tauri.
The private key must be password-protected. Do not use real values for testing; local testing uses
one-off synthetic keys and `AI Router QA.app`.

## Version and tag

`src-tauri/tauri.conf.json` is the manual version source. Change the stable SemVer first, then run:

```sh
pnpm version:sync
pnpm version:check
```

`version:sync` only projects that value into `package.json`, the root `Cargo.toml`, and the two local
workspace packages `ai-router-app` and `router-core` in `Cargo.lock`; do not edit these projections by
hand afterward. The sync preserves other bytes and dependency versions. Review the full diff to
confirm that only those version fields changed, and then let `version:check` verify the relationships
across all projections.

After determining the candidate scope and confirming the local stable tag is up to date, run this
before creating the tag:

```sh
pnpm release:inventory
```

This read-only command selects the highest annotated stable SemVer tag reachable from `HEAD`, lists
every commit and changed path from that baseline to the candidate `HEAD`, and reports the full commit
IDs on both sides and the candidate version. The release owner must dispose of every item in the
inventory: write all user-visible additions, behavior changes, bug fixes, compatibility notes,
migration actions, and restart impacts into the release notes, and record a concise exclusion reason
for changes that are not written in, such as tests, dependencies, or internal refactors. Also
cross-check against available merged PRs and completed task evidence, because local Git metadata
cannot automatically prove semantic completeness. Final accuracy, priority ordering, and completeness
are approved by the release owner.

After that inventory, committing the release notes, merging, and confirming required checks, create
the identical `v<version>` tag on that immutable commit. The workflow re-compares the repository,
`GITHUB_REF`, the tag, the app version, the checkout `HEAD`, and the tag commit; prereleases, build
metadata, a moved tag, or version drift all fail closed.

## Release notes

Every candidate stable version must commit `release-notes/v<version>.md` before the tag is created and
after the item-by-item `pnpm release:inventory` review. The file uses a strict structure:
`# AI Router release v<version>`, a `Highlights` section containing one to three bullet items, and
optional `Fixes` and `Notices` sections. A tool or AI may produce a draft, but the release owner must
verify user-visible changes, compatibility, and operator notices and review the final content in an
ordinary pull request.

This file is the sole content source for the GitHub Release body and `latest.json.notes`. Missing
content, a version mismatch, placeholder content, duplicate items, invalid Markdown, or content
beyond the bounds all make the release fail. The full format and checklist are in
[`release-notes/README.md`](../../release-notes/README.md). Do not maintain release notes separately
in the GitHub UI or in the generated `latest.json`.

## Workflow order

1. `release:validate` validates the version, tag, commit, reviewed release notes, and updater
   public-key shape.
2. `release:draft` creates a draft with the reviewed release notes; a rerun repairs the body for the
   same commit and cleans up assets, while an already published Release hard-fails.
3. `release:build` injects the public key through a temporary `0600` configuration and produces the
   ad-hoc-signed DMG and the Tauri updater archive/signature.
4. `release:prepare` checks the identifier, version, macOS 13, arm64, `Signature=adhoc`, and absence of
   a Developer ID authority in the app and the DMG, verifies the updater signature (including that the
   version binding in the signature trusted comment equals this release version, failing at the draft
   stage if it is missing or mismatched), generates `latest.json` and `SHA256SUMS`, and downloads the
   draft assets back for a byte-for-byte comparison after upload.
5. A SHA-pinned GitHub attestation action generates provenance for the complete asset directory.
6. `release:publish` reads back and verifies the draft assets, the manifest notes, and the Release body
   once more, then switches to published in a single final step.

The base `tauri.conf.json`, the QA configuration, and `pnpm tauri:source:build` do not create updater
assets and do not consume release secrets. Only the temporarily merged `tauri.release.conf.json`
enables the DMG, the updater artifact, and `signingIdentity: "-"`.

## Post-release checks

- The Release is no longer a draft and the tag still points to the workflow's source SHA;
- the five asset names and sizes match `SHA256SUMS`;
- GitHub shows provenance for every published asset;
- the Release notes mark the DMG as the first-install entry point and state clearly that there is no
  Apple verification or notarization;
- verify current/newer/malformed/offline/signature-failure/install/restart with an isolated one-off
  updater QA root; these one-off artifacts must be signed with
  `tauri signer sign --app-version <version>` (CLI ≥ 2.11.5), otherwise builds with
  `requireSignedVersion` reject them for a missing version binding;
- read the production PID and bundle path before and after QA to confirm the production
  `AI Router.app` was not quit, replaced, started, or restarted.

The first updater-capable version only verifies the manual DMG bridge. The first real in-app upgrade
must upgrade from that bridge version to a higher stable QA version and keep using
`com.relax.airouter.qa` for destructive lifecycle acceptance.

## Failure handling

A failed run leaving a draft is the expected safe state. After fixing the code or environment, rerun
while the tag has not moved and the source commit has not changed; the script rejects a published
Release, a different target commit, or an incomplete remote state. Do not delete or overwrite
published assets, and do not move old tags. If any error is found in a public version, fix it, bump the
patch version, and publish a new tag.

If the updater private key is suspected of leaking, stop the workflow, remove the environment secret,
and require a manual DMG upgrade per the leak path requirements in
[Release and app updates](./application-updates.md).
